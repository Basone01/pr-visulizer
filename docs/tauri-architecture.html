Tauri Desktop Mode — Architecture

pr-visualizer <github-pr-url> as a desktop app: no server process, no OAuth — auth borrowed from the gh CLI. Companion to docs/tauri-architecture.md.

1 · Before / after — what moves, what appears

Before
packages/shared contract + ranking apps/server routes, auth, progress store githubGateway/ ← moves analysis/ ← moves utils (diff/path/lang) ← move apps/web SPA · PrClient seam (http | fixture)
After
packages/shared (unchanged) packages/engine ← NEW (extracted, not rewritten) FastAstEngine · treeSitter(+GrammarSource seam) gateway iface + octokit + fake · utils · cache apps/server thin BFF shell — consumes engine apps/web SPA · PrClient (http | fixture | tauri) apps/desktop ← NEW · Tauri 2 shell (Rust ≈ 0 custom)

Dependency direction stays clean: desktop → web → engine → shared and server → engine → shared. The BFF survives for the hosted-web deployment and keeps its 9 integration tests guarding the engine.

2 · Three entry paths, one review screen

It's a normal installed app first. tauri build ships a standard .app/installer — double-click from the Dock and you land on the home screen; no terminal required. The CLI is an optional shim over the same binary.

A — CLI arg (optional)

pr-visualizer <pr-url> → straight to the review screen (deep link). Accepted forms: full URL, owner/repo#42, owner/repo/42. The shim execs the same installed binary; Single Instance focuses an open window.

B — paste a URL

Open the app plain → home screen with a parse-as-you-type input; a valid target enables Go, invalid shows the accepted forms inline.

C — watched repos

Add owner/repo once (persisted in the Store plugin) → home screen lists that repo's open PRs (via listOpenPullRequests, one Octokit call). Click a PR → review.

    4 · The three seams — Tauri adds implementations, never seams

    Seam 1 — PrClient (exists)

    apps/web/src/service/prClient.ts — six methods the whole SPA depends on. Tauri mode is a third implementation picked in clientFactory.ts; zero component changes.

    Seam 2 — GithubGateway (exists)

    Octokit runs in webviews; only CORS blocks it. Tauri's official HTTP Client plugin is a Rust-side client (no CORS), and Octokit accepts an injected fetch — same gateway, different fetch.

    Seam 3 — GrammarSource (the ONE refactor)

    treeSitter.ts resolves grammar wasm via createRequire — node-only. Extract a (grammarId) ⇒ Promise<Uint8Array> setting: node reads from tree-sitter-wasms, the webview fetches bundled Vite assets. Everything else in the file moves untouched.

    5 · TauriPrClient — method by method

    PrClient method In-webview implementation
    getAnalysis run createFastAstEngine({ gateway }).analyze(target) directly — no 202 polling; the promise is the progress signal
    getPatch from the gateway's PR file list (already fetched, cached per headSha)
    get/putProgress Tauri Store plugin JSON, key owner/repo#n@headSha, re-parsed through shared reviewProgressSchema on read
    submitReview gateway → POST /pulls/:n/reviews — same Octokit call the BFF makes
    deepen(target, onProgress) deep v1, desktop-local (§6 main doc): resolve the clone-root setting (reject NeedsCloneRootError when unset → the UI opens the folder picker), clone/fetch the PR head through the clone manager, build RepoFiles from the checkout, run createDeepEngine({ gateway, repoFiles, grammarSource }), and cache it so getAnalysis(target, "deep") returns it. onProgress reports cloning / fetching / checking out / analyzing
    listOpenPullRequests gateway → GET /repos/:o/:r/pulls?state=open — feeds the home screen's watched-repos picker (browser mode: new BFF route)

    Deep mode (v1) — desktop-local clone

    Deep v1 (§6 main doc) is wired into the desktop app: a full clone + repo-wide tree-sitter index, run on the user's own disk. No server worker, no SCIP — that stays the §6.2 precision tier behind the same AnalysisEngine interface.

    • Clone-root setting. The user picks ONE folder (native picker, @tauri-apps/plugin-dialog), persisted in app storage under cloneRoot and reused across every PR. The first Deepen press with no folder set rejects NeedsCloneRootError → a modal explains deep mode + "Choose folder…"; a gear reopens it to show/change the folder.
    • Clone layout — <cloneRoot>/<owner>/<repo>, one worktree per repo. Fresh: gh repo clone <owner>/<repo> <dir> (gh carries private-repo auth) then fetch + checkout the PR head. Reuse: git -C <dir> fetch origin pull/<n>/head then git -C <dir> checkout --force --detach FETCH_HEAD. Dir exists but not a git repo → error; dirty worktree → --force (our cache dir); fetch/auth/network failures surface stderr on the top bar.
    • RepoFiles — listing via git -C <dir> ls-files (respects .gitignore); reads via @tauri-apps/plugin-fs readTextFile.
    • Folder-picker ↔ fs-scope (verified, Tauri 2 docs, 2026-07). A directory chosen through the Dialog open() picker is automatically added to the fs runtime scope, so readTextFile under it works in the same session. That grant is not persisted alone — tauri-plugin-persisted-scope (registered after fs) saves it to disk so a cloneRoot survives restarts. Fallback if it proves unreliable: git -C <dir> show HEAD:<path> (correct but one process per file).
    • Capability scopes added (minimal): dialog:allow-open, fs:allow-read-text-file, fs:allow-exists, and shell:allow-execute entries with anchored per-arg validators — gh-repo-clone, git-fetch-pull, git-checkout-detach, git-ls-files.

    6 · Security posture

    Token

    Webview memory only — never in the Store file, a URL, or a log. Comes from gh auth token; gh owns storage + refresh.

    Plugin scopes

    Shell pinned to exactly gh auth token; HTTP allowlist api.github.com only. A compromised webview can't run arbitrary commands or exfiltrate elsewhere.

    Error UX

    gh missing → install hint · not authed → gh auth login hint · bad URL → usage help · no repo access → GitHub's 403/404 with repo name.
