PR Review Visualizer — Architecture

A web app that turns a GitHub PR into a dependency graph, tells the reviewer where to start and what to review next, and submits the review back to GitHub. Companion to docs/architecture.md.

1 · System shape — SPA + thin backend (BFF)

Browser — React SPA

  • Graph view — node graph of changed files, review order
  • Diff panel — rich per-file diff (shiki), symbol annotations
  • Review tray — checkmarks, draft comments, submit
▲ ▼   HTTPS JSON · httpOnly session cookie (token never reaches the browser)

BFF — Node + TypeScript (Fastify)

  • Auth service — GitHub OAuth, encrypted token vault
  • GitHub gateway — Octokit wrapper, ETag cache
  • Analysis service — two engines, one contract: FastAstEngine (tree-sitter, in-process, default) · DeepLspEngine (enqueue → worker, opt-in); results cached by (headSha, engine) — immutable, no invalidation logic
  • Review service — progress store (SQLite), review submit
▲ ▼   job queue — deep mode only

Analysis worker(s) — deep mode only

  • shallow clone @ headSha → SCIP indexer per language → repo-wide reference graph
  • sandboxed: never executes repo code, --ignore-scripts, CPU/disk quotas, per-job timeout
  • on failure/timeout the fast result simply stands
▲ ▼   REST + GraphQL (Octokit) · git clone (worker)

GitHub API

  • PR meta + diffs + file contents @ headSha
  • markFileAsViewed (GraphQL) — syncs our checkmarks to GitHub's native "Viewed"
  • POST /pulls/:n/reviews — the real review submit

3 · Two analysis engines, one contract — the user chooses

Both engines implement AnalysisEngine and emit the same AnalysisResult — the graph UI, ranking, and review flow never know which one ran. Fast runs automatically on PR open; the reviewer can click "Deepen analysis" to upgrade the same graph in place. Checkmarks and drafts survive the swap (progress is keyed by headSha, not by engine).

Fast — AST (default)

Reads changed files only (+1-hop imports) via the GitHub API. tree-sitter parse + name resolution. Seconds, no extra infra. Misses dynamic dispatch and anything outside the diff.

Deep — LSP-grade (opt-in)

Worker shallow-clones the whole repo at headSha and runs SCIP indexers (batch "find-references everywhere" — same precision as LSP, right shape for a job). 1–10 min, needs queue + workers + sandbox. Compiler-grade edges, repo-wide.

What deep mode adds: blast radius

On PR #42, suppose an unchanged file admin.ts also calls withRateLimit. The fast engine can't see it — it never reads unchanged files. The deep engine shows it as a dashed ghost node: context, never part of the review queue.

4 · Ranking is a controllable core with presets

The sort priorities live in one RankingPolicy object — swapping a preset changes the order, not the algorithm.

foundations-first (default)

topoLevel ↑ → fanIn ↓ → churn ↓. Dependencies before dependents — what the walkthrough above uses.

blast-radius-first

fanIn ↓ first (+ blastRadius when deep data is present). Start at the file most is built on, regardless of level.

quick-wins

churn ↑ first. Small files first to warm up, then the big ones.

5 · Review-submit flow (checkmarks → real GitHub)

  1. Reviewer clicks ✓ on a file → SPA optimistic update → PUT /progress → BFF saves to SQLite and fires GraphQL markFileAsViewed — the checkmark appears in GitHub's native UI too.
  2. Inline comments are drafted app-side in ReviewProgress.drafts — invisible to GitHub until submit.
  3. Submit → POST /repos/:o/:r/pulls/:n/reviews with { commit_id: headSha, event: APPROVE | REQUEST_CHANGES | COMMENT, comments: [{path, line, side, body}] } → one real GitHub review, comments anchored to lines.
  4. Force-push guard: a new headSha re-triggers analysis; drafts are remapped by hunk proximity, and any comment that cannot be remapped is flagged — never silently dropped.
